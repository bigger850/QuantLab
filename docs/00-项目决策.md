# QuantLab 项目决策记录

> 记录选型依据、踩坑过程与后续计划。后续改动先看这里，避免重复讨论。

## 一、定位与合规边界

**定位**：A 股数据与研究工具。行情展示 + 指标计算 + 历史回测 + 因子筛选。

**边界**（不可越过）：
- 不做投资建议、不推荐个股买卖点、不承诺收益
- 不接交易通道、不做代客理财、不碰资金
- 页面常驻「仅供研究，不构成投资建议」

原因：投顾业务需牌照，代客理财涉资金池，两条线都不能碰。剩下的空间足够做一个正经的技术项目。

## 二、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Java 21 | 目标岗位是 Java 后端，且 LTS 支持到 2029 |
| 框架 | Spring Boot 3.3 | 与 Java 21 匹配，生态稳定 |
| ORM | MyBatis-Plus | 复杂查询可控，比 JPA 更贴合国内 Java 岗 |
| 数据库 | MySQL 8.0 | 本地已有，窗口函数可用 |
| 缓存 | Redis 6 | 行情缓存 + 同步锁 + 进度上报 |
| 前端 | Vue 3 + Vite | 上手快，构建快，不需要 SSR |
| 图表 | ECharts 5 | K 线/蜡烛图开箱即用，国内文档好 |
| 部署 | Docker Compose | 一键起四件套，不需要 K8s |

## 三、数据源踩坑

**第一选择是东方财富**，因为接口最全（清单 + K线 + 实时一站解决）。

实测结果：前几次请求成功（茅台 6041 根日线正常返回），随后连接被持续重置，Java 端报 `HTTP/1.1 header parser received no bytes`。排查确认不是网络全局问题（百度、腾讯均 200），是东财对本机 IP 的连接拦截。

**改用双源方案**：

| 用途 | 源 | 限制 |
|---|---|---|
| 标的清单 | 新浪 `Market_Center.getHQNodeData` | 需 Referer，100 条/页，约 66 页 |
| 日线 | 腾讯 `fzqkline/get`（前复权） | 单次约 640 根，按 2 年分段 |
| 实时 | 腾讯 `qt.gtimg.cn` | GBK 编码，按字节解码 |

代价：腾讯日线不返回成交额，按 `成交量(手) × 100 × 均价` 估算，只用于排序，不参与回测计算。

**限流教训**：8 并发 + 30ms 间隔时失败率 39%，且失败集中在连续区段（典型限流特征）。降到 4 并发 + 150ms 间隔后失败率降到 21%。同步任务必须支持增量补跑，否则一次限流就要从头再来。

## 四、关键设计

**回测防未来函数**：第 `i-1` 根收盘出信号，第 `i` 根开盘价成交。参数 `signals[i-1]` 的索引位置是刻意的。

**日线表主键**：`(code, trade_date)` 复合主键，不用自增 ID。InnoDB 按主键聚集，单标的区间查询是顺序扫描，省掉二级索引回表。代价是不能用 MyBatis-Plus 的 `selectById`，全部走自定义 SQL。

**同步幂等**：`INSERT ... ON DUPLICATE KEY UPDATE`，重复跑不会产生脏数据，也不用先删后插。

**分布式锁**：Redis `SETNX + TTL 3h`。进程被 kill 时锁不会自动释放，需要手动清 `quant:sync:lock`——这是已知缺陷，二期改成带续期的锁。

## 六、已知问题

1. 同步被限流时部分标的失败，需重跑增量补齐（二期做自动重试队列）
2. 同步锁依赖人工清理，进程异常退出后会锁 3 小时
3. 只做日线，无分钟级；回测单标的单仓位，不支持组合
4. 无用户体系，自选股表未做账号隔离
5. 成交额为估算值，与真实成交额有偏差
